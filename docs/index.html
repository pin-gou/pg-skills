1. 这是什么

pg-skills 是一个共享能力层，通过 git subtree 嵌入到你的项目 .pg/skills/ 下。它为 AI 编码助手补上它自己看不见的东西——真实环境的互动方法。

AI 写代码不可怕，可怕的是——写完没人敢合。

大模型扫得懂整个代码库，却答不上来：项目怎么构建？在哪个环境验证？什么算"改对了"？这些答案不在代码里，在真实环境里。

它解决什么问题

没有 pg-skills

AI 猜构建命令、猜环境地址、猜验收标准。能编译、单测能过，一跑真实服务就崩——"幻觉完成"。

有了 pg-skills

project.yaml 白纸黑字写清模块/环境/实例/构建命令。hook 协议让 AI 能启动、重启、观察真实服务。自动驾驶模式强制"启动实例并验证结果"才算完成。

核心概念

概念一句话
project.yaml给 AI 的"户口本"——模块、环境、实例、构建/测试命令，唯一可信源（SSOT）
Hook 协议环境生命周期接口：prepare_env / start / stop / logs / health_check，注入 PG_* 环境变量，写 result.json，统一审计
pg-auto-pilot唯一工作流——不限定 LLM 怎么做，只要求：计划含"启动实例并验证结果"；执行前让用户选定环境
工具适配器核心流程与工具无关，由适配器渲染到 OpenCode / Mobile Coder / DeepSeek Harness

工作方式

人只做两件事：说清需求、在关键节点点头。中间的实现 + 验证由 AI + hook 协议自动跑完。合并到 default 分支由人手动 git merge 收口。

仓库结构

pg-skills/
├── src/
│   ├── core/workflows/        # 工具无关的规范源：1 个 command、1 个 skill、1 个 sub-agent
│   │   ├── commands/pg-0-auto-pilot.md
│   │   ├── skills/pg-auto-pilot/
│   │   ├── agents/explore.md
│   │   └── scripts/pg-parse-config.py   # SSOT 查询工具
│   ├── integrations/          # 工具适配器：opencode / mobile_coder / deepseek_harness
│   └── runtime/               # CLI + hook 执行引擎 + SSOT 规范
│       ├── bin/               # pg, pg-invoke-hook.py, pg-run, pg-exit, pg-fail
│       ├── lib/               # hook-helpers.sh, pg-run-hook.py, tui.py
│       └── spec/              # project.schema.json, error-categories.yaml, hook-env-vars.yaml
├── examples/shell/hooks/      # 默认 hook 模板
└── VERSION                    # 1.0.0

一句话总结：pg-skills 为 AI 补全真实环境的互动方法——project.yaml 定义"项目长什么样"，hook 协议定义"在哪验证"，pg-auto-pilot 强制"启动实例并验证结果"。

2. 快速接入

四步接入

# ① git subtree 拉入 pg-skills（版本号与 VERSION 一致）
git remote add pg-skills git@github.com:pin-gou/pg-skills.git
git fetch pg-skills
git subtree add --prefix=.pg/skills pg-skills v1.0.0 --squash

# ② 初始化骨架 + 安装工具适配器
python3 .pg/skills/src/runtime/bin/pg init

#    非交互环境（CI）必须显式指定工具
python3 .pg/skills/src/runtime/bin/pg init --non-interactive --tool opencode

# ③ 重启开发工具，加载新的 command/skill/agent

# ④ 验证接入
python3 .pg/skills/src/runtime/bin/pg doctor

pg init 工具选择规则

  • 传入 --tool：直接安装指定适配器，不做探测
  • 未传且只检测到一个工具：显示依据，要求确认
  • 未传且检测到多个：列出候选项，由用户选择
  • CI / 非交互环境：必须传 --tool，否则失败
flag用途
--tool <id>显式安装适配器（opencode / mobile-coder / deepseek-harness）
--list-tools列出当前支持的开发工具
--non-interactive禁止提示；必须显式 --tool
-y / --yes只探测到一个工具时免确认
--no-tool-config仅初始化 .pg/ 骨架，不安装工具适配

接入后的 .pg/ 骨架

.pg/
├── project.yaml              # 配置 SSOT（modules / environments）
├── hooks/                    # 环境生命周期脚本
├── agent/                    # pg-agent 日志与产物
├── ad-hoc/                   # ad-hoc 调用日志
├── context/                  # 项目上下文（agent-protocol.md 等）
├── skills/                   # 嵌入的 pg-skills
└── runs/                     # 运行记录

接入 Checklist

  • git subtree add --prefix=.pg/skills pg-skills v1.0.0 --squash
  • pg init 生成骨架 + 渲染工具适配
  • pg doctor 校验通过
  • 核对 project.yaml：modules / environments 与真实项目一致
  • 核对 hooks：每个 role 的 start/stop/logs，每个 env 的 prepare_env/clean_env
  • 重启开发工具，运行 /0-pg-auto-pilot 跑通一次
接入最重要的两件事：写对 project.yaml（骨架）、写对 hooks（血肉）。这两件不对，AI 再怎么跑都是错的。

3. project.yaml 配置

project.yaml 是给 AI 的"户口本"——唯一可信源。Agent 必须通过 pg-parse-config.py 读取，禁止直接读 YAML。

两段核心配置

modules — 代码模块 + build/lint/test 命令

modules:
  backend:
    root: webvirt-backend
    language: java
    build: .pg/hooks/backend-build.sh
    lint: cd webvirt-backend && mvn checkstyle:check
    test:
      unit: { cmd: .pg/hooks/backend-test.sh, timeout_seconds: 3600 }
注意：modules.build 虽然可以指向 .pg/hooks/ 下的脚本，但它被 runner 当作普通 shell 命令执行——没有 PG_* 注入，不走 hook 协议。是否走 hook 取决于配置在 project.yaml 的哪个位置，不在于是不是脚本文件。

environments — 运行时拓扑 + 启停动作

environments:
  dev-local:
    description: "本机全栈开发"
    prepare_env:  { script: .pg/hooks/env-dev-local-prepare.sh, timeout_seconds: 300 }
    clean_env:    { script: .pg/hooks/env-dev-local-clean.sh, timeout_seconds: 120 }
    roles:
      - name: backend
        instances:
          - { name: backend-1, host: localhost, port: 9080 }
        actions:
          start: { script: .pg/hooks/role-backend-start.sh, timeout_seconds: 300 }
          stop:  { script: .pg/hooks/role-backend-stop.sh, timeout_seconds: 30 }
          logs:  { script: .pg/hooks/role-backend-logs.sh, args: ["{lines:100}"] }
          health_check: { url: http://localhost:9080/health }

v0.9.2 破坏性变更：roles 已由键值对改为数组格式（[{name, ...}]），旧写法将解析失败。

SSOT 查询 — pg-parse-config.py

Agent 必须通过此工具读取配置：

目的命令
拿全部 modules + environmentspg-parse-config.py pg-agent
拿单个模块 build 命令pg-parse-config.py --resolve-module-build <module>
拿单个模块 test_keypg-parse-config.py --resolve-module-test <module> <test_key>
拿环境的 role 信息pg-parse-config.py --resolve-env <env>
拿单值pg-parse-config.py --key <dotted.path>
拿子树pg-parse-config.py --prefix <top-level-key>
  • 禁止直接读 .pg/project.yaml——绕过 SSOT 可能拿到 stale 副本
  • 不要用已移除的 skill 模式调用（如 pg-build / pg-propose）——只有 pg-agent 是 agent 专用入口

Hook 协议边界

维度走 hook 协议？配置位置
Environments
prepare_env / clean_env / role start·stop·logs·health_check		 走 hook .pg/hooks/<name>.sh
Modules
build / lint / test		 不走 hook project.yaml modules.<m>.{build,lint,test}

Hook 调用 — 必须走 pg-invoke-hook.py

# agent 调用（固定 --caller pg-agent + 一次性 session）
python3 .pg/skills/src/runtime/bin/pg-invoke-hook.py \
  --caller pg-agent --session "$SESSION_ID" \
  --env dev-local --role backend --instance backend-1 --action start

# 用户手工：pg-run 交互菜单或 CLI 直达
./pg-run --env dev-local --role backend --instance backend-1 --action logs --tail-lines 20
禁止：直接 bash .pg/hooks/role-backend-start.sh——绕过协议、缺 PG_* 注入、不写 result.json、审计不可见。

日志路由

callersession 形式日志路径
pg-agent<iso-date>-<keyword>（如 2026-09-12-fix-login）.pg/agent/<session>/<env>/logs/
ad-hoc留空自动生成 auto-<date>-<pid>.pg/ad-hoc/<session>/<env>/logs/

action 速查

级别action参数要求
per-rolestart / stop / restart / logs / tail / health_check--role + --instance
env-levelprepare_env / clean_env / restart_all_instances忽略 role/instance

4. pg-run 交互菜单

./pg-run 是用户操作环境与模块的首选入口——无需记住 CLI 参数，逐级菜单引导选择并执行。内部自动走 hook 协议（--caller ad-hoc --session manual），与 agent 调用同一套机制。

五个 Tab

Tab快捷键功能
常用操作f一键组合：准备环境并启动所有实例 / 停止所有实例并清理 / 启动所有实例 / 停止所有实例
Environmente环境级操作：prepare_env / clean_env
Instancei实例级操作：选 role → 选 instance → start / stop / health_check / logs / tail
Modulem模块操作：选 module → build / lint / test.*
更新u查看当前版本、列出远程可用版本（main 置顶、每页 10 项）、选中后 y/N 确认强制更新

启动后先选环境（env），再进入 Tab 菜单。Tab 键或快捷字母切换 Tab，数字键选择条目，b 返回上一级，c 换环境，q 退出。

交互模式

# 启动交互菜单
./pg-run

# 启动后先选环境，然后进入五 Tab 菜单：
# ┌─ pg-run — dev-local ────────────────────┐
# │ Tab: 常用操作|Environment|Instance|Module|更新 │
# │ 常用操作: 准备并启动 / 停止并清理 / ...        │
# └─────────────────────────────────────────┘

CLI 直达模式

跳过菜单，直接执行操作。参数齐全时 pg-run 不会进入交互模式：

# 常用操作
./pg-run --env dev-local --action prepare_env_and_start
./pg-run --env dev-local --action start_all_instances
./pg-run --env dev-local --action stop_all_instances

# 环境级操作
./pg-run --env dev-local --action prepare_env
./pg-run --env dev-local --action clean_env

# 实例级操作（需 --role + --instance）
./pg-run --env dev-local --role backend --instance backend-1 --action start
./pg-run --env dev-local --role backend --instance backend-1 --action stop
./pg-run --env dev-local --role backend --instance backend-1 --action logs

# 模块操作
./pg-run --module backend --action build
./pg-run --module backend --action test.unit

# 直接执行 shell 命令（不走 hook 协议，不注入 PG_*，仅供调试）
./pg-run --cmd "curl -s localhost:9080/health"
小提示：logs 是只读操作，适合用来验证 hook 脚本是否正常加载。安全无害，不启停服务、不写 DB。

5. pg-auto-pilot 自动驾驶

/0-pg-auto-pilot 是当前唯一保留的工作流。它不限定 LLM 如何规划与执行，只提两条要求：

要求 1：实施计划必须包含"启动实例并验证结果"

  • 启动实例：在选定的环境中把对应 role 的实例跑起来（走 hooks 协议）
  • 改完代码必须重启实例：即使实例已在运行，也不得跳过 start/restart——不重启的话运行中的进程仍持有旧代码
  • 验证结果：手段不限——build / lint / test、health_check、运行时检查等
  • 验证不通过 → 修复 → 重验，直到通过或上报用户

要求 2：执行计划前，先让用户选定环境并确认准备方式

  • 选定环境：哪个 env（如 dev-local）
  • 是否需要准备环境：需要 → prepare_env 后再启动；已就绪 → 跳过准备，直接启动

典型流程（仅供参考，可自由裁剪）

0. 明确任务范围 → 形成实施计划（必须含"启动实例 + 验证结果"）
1. 执行前：请用户选定环境 + 确认是否需要准备环境
   → 需要准备 → prepare_env（env-level）
   → 已就绪 → 跳过准备，直接下一步
2. 启动所需实例：--action start（--role ... --instance ...）
   → 改完代码后必须 restart（或 stop+start）再启动
   → health_check 通过才算就绪
3. 执行编码工作 + 验证：build/lint/test、运行时检查等
   → 失败 → 修复 → 重验
4. [可选] 收尾：--action logs / tail 确认运行日志无异常
5. 汇总报告：改动内容、验证结果、hook 日志位置
使用边界：不要求落盘 proposal/design/tasks、不派发 sub-agent、不定义阶段状态机、不负责合并（用手动 git merge）。

Hook 失败时的处理

categoryseverityagent 处理
port_in_userecoverable解除端口冲突后重试
timeout / networkrecoverable指数退避重试
health_check_fail / dependency_not_readyrecoverable等待再重试
test_failure / build_failurerecoverable定位修复后重试
prereq_missing / config_invalid / permission_denied / resource_exhaustedblocked上报用户，不自行绕过
db_migration_fail / invariant_violationblocked上报用户
红线：禁止直接 bash .pg/hooks/*.sh；禁止硬编码 host/port（一律从 project.yaml 读）；任务结束必须换新 session-id。

常见问题

接入后要重启开发工具吗？

要。工具需要重启才会加载新的 command / skill / agent。没重启就看不到 /0-pg-auto-pilot。

怎么升级 pg-skills？
pg upgrade            # 升级到最新 main
pg upgrade v1.0.0     # 升级到指定 tag
pg upgrade --list     # 查看远程可用版本
pg doctor             # 升级后校验
怎么验证 hooks 写得对不对？

用 ./pg-run 的 logs 动作（只读，安全）验证 hook 能正常加载；再 start/stop 一个 role 做端到端验证：

./pg-run --env dev-local --role backend --instance backend-1 --action logs --tail-lines 10
./pg-run --env dev-local --role backend --instance backend-1 --action start
./pg-run --env dev-local --role backend --instance backend-1 --action stop
日志找不到，去哪找？

agent 调用：.pg/agent/<session>/<env>/logs/；ad-hoc 调用：.pg/ad-hoc/<session>/<env>/logs/。多半是 session-id 拼错或跨任务复用。不要去找 scripts/logs/——那只是兜底路径。

module 命令和 hook 脚本的区别？

看它在 project.yaml 中的位置：modules 下的都是 module 命令（无 PG_* 注入，只看 exit code）；environments 下的都是 hook（有 PG_* 注入，写 result.json）。

hook 报错 "environment not found" 或 "role not defined"？
python3 .pg/skills/src/core/workflows/scripts/pg-parse-config.py --prefix environments

大概率是 env 名 / role 名写错，或 --caller pg-agent 忘了传 --session。
