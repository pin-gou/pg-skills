1. 为什么需要品构

AI 写代码不可怕，可怕的是——写完没人敢合。

大模型扫得懂整个代码库，却答不上来四个问题：项目怎么构建？在哪个环境验证？什么算"改对了"？每一步谁复核过？

这些答案代码里没有，但是品构 pg-skills 为 AI 补全了这份空白。

品构 = SEA-Driven Development（方案 · 环境 · 验收）——SDD 的延伸，三种要素，缺一不可。

1.1 同一个需求，两种命运

❌ 盲猜模式

AI 读到代码，但猜构建命令、猜环境地址、猜验收标准——猜对了是运气，猜错了是"写完不敢合"。因为没人说得清它改对了没有、验证过没有。

✅ 品构模式

先出图纸（propose）→ 按图施工（build）→ 真实环境验证 → 门控打分 → 合入。每一步都有结构兜底，系统比人先看见问题。

1.2 一份户口本 + 无人值守的一天

project.yaml 就是给 AI 的户口本：模块 / 环境 / 实例 / 构建命令 / 验证方式，白纸黑字。故名「品构」——品质，长在结构里。AI 不再猜，照章办事。

人只做两件事：说清需求、在关键节点点头。中间那 1-8 小时的实现 + 验证，全部由 pipeline 引擎自动跑完——你不参与。

1.3 品构的方法论：SEA-Driven Development

「品构」是品牌，藏着哲学——品质，长在结构里。那"结构"具体指什么？答案在它的方法论里：SEA-Driven Development（方案 · 环境 · 验收）。

SEA 是对 SDD（Specification-Driven Development）的延伸。SDD 的核心是先写方案再写代码，但传统 SDD 缺两样东西——它不关心真实环境长什么样，也不告诉你"验证通过"是在真环境跑的还是在 mock 里跑的。品构在方案之外加了两个同等级别的支柱，凑成完整的 SEA：

支柱是什么解决什么问题
方案 Specproposal / design / tasks做什么、怎么做、怎么验证
环境 Environmentenv-description.yaml（describe_env 只读探测）真实环境快照——有哪些 DB、版本多少、数据状态如何，不再猜
验收 Acceptancescenario-*.yaml（Gherkin 场景）验收不是在 mock 里跑，而是在真实服务实例上跑 Given / When / Then

三根支柱加在一起，才是品构说的"结构"。缺了环境，方案写的是"假设中的环境"；缺了真实验收，验证跑的是"理想中的验证"。只有三者合一，系统才能完整地描述"项目长什么样 → 在哪验证 → 怎么算真通过"。

品质，长在结构里——SEA 就是那套把抽象"结构"落到实处的三根支柱。

1.4 为什么敢合

三步质检，让"敢合"不是靠感觉：

  • 每步留痕可回放 —— 每个操作都是不可变事件，随时可以复盘
  • 验证在真实环境 —— 启动真实服务、跑真实 API、查真实日志，不是 mock 里跑一跑
  • 门控打分 ≥80 才放行 —— 5 维加权评分，没评审就不合入，没验证就不交付

交付不是终点。回归发现问题 → 自动修复 → 提交 PR，闭环兜底。

使用 pg-skills 的日常体感

这是开发者用 pg-skills 跑一个 change（一次变更）时，时间线上大致发生的事：

  1. /1-pg-define — 约 20 分钟
    跟 AI 对齐"这次变更要做什么 / 不做什么 / 边界在哪"，并在真实环境里讨论验收方法
    产出：口头 scope summary + define-summary.yaml + env-description.yaml（需求边界 + 验收方法 + 环境引用）
  2. /2-pg-propose — 自动
    按定义生成完整的 spec 链路：
    • proposal.md — 这次变更为什么做、做什么
    • design.md — 技术方案
    • tasks.md — 任务拆分（每个任务 2-5 分钟可完成粒度）
    • execution-manifest.yaml — 本次执行的 SSOT
    • scenario-<track>.yaml — 真实环境 E2E 场景定义
  3. /3-pg-build — 1-8 小时（取决于变更规模）· 无人工干预
    编排器自动跑完：
    • 自动准备环境（按 manifest 的 stage→env 映射调 hook）
    • 自动写失败的测试（TDD 红 phase，确认真的失败后才进入实现）
    • 自动写实现代码 · 自动做代码 Review
    • 自动门控检查（gate + final-gate）
    • 真实场景验证（Scenario 真起 dev/staging 环境跑端到端）
    跑完直接产出一个可以验收的 change。
  4. 你验收 — 几分钟
    大多数情况下（约 80%）一次就达到预期，直接合并；
    剩余约 20% 的情况，AI 的产出跟预期有偏差——你用 vibecoding（人机对话微调）做细微调整即可达到预期。

长期迭代回路：跑完一轮后，产品上线不是终点。pg-skills 还有两条自动回路：

  • 自动回归：/4-pg-regression <suite> 选定测试套件，自动初始化环境跑回归，对失败的测试自动修复脚本（不创建 PR），对失败的生产代码自动修复并创建 PR 给你审；
  • Bug 修复：/5-pg-fix-issue 拿到 bug 描述后，按 propose → build 同款流程产出修复 patch。

开发者要做的两件事：

  1. 定义每个 change 的边界（用 /1-pg-define 想清楚要做什么 / 不做什么）；
  2. 验收每个 change 的结果（看 build 产物是否符合预期，不符合就 vibecoding 微调；之后审 /4-pg-regression 提的 PR 即可）。

中间那 1-8 小时的实现 + 验证过程，全部由 pg-skills 在事件溯源 pipeline 引擎上跑完——人不参与。

1.5 AI 在每一步的角色

「品质，长在结构里」——这里「写出」二字要分开看：

流程AI 角色是否署名谁兜底
定界 /1-pg-define 半结构化"准出图员"：扫 repo、把模糊表达收成 in/out of scope AI 决策部分：辅助澄清；最终签名 = 人 人用 question 工具三选一
提案 /2-pg-propose 被规训的"出图员"：填 proposal / design / tasks 骨架 + 出 execution-manifest.yaml AI 全程写；产物必含 proposal / design / tasks / execution-manifest.yaml 5 项 common decisions 已固化；产物生成后直接进入 build
构建 /3-pg-build 受约束的"代码工人"：被 TDRVG + stages × tracks pipeline 约束的 sub-agent 派遣 每段 commit 写明 dispatch 来源（dispatch file） events_log 全留痕；replay 可重放；review cycle 独立计数
回归 /4-pg-regression 测试修缮工（带边界）：fix-test 只修 A/B 类（断言漂移 / 选择器过期），C 类（生产 bug）不碰 改的就 commit；不改的就拉问题清单走 fix-issue pg-check-fix-test-boundary.py 二次守门
修复 /5-pg-fix-issue 受环境探测约束的"诊断员"：describe_env 探测环境 → 诊断根因 → 展示修复方案 → 用户确认 → 改代码 每个动作落 commit；验证失败的 commit 标 [ ] 待继续 真实环境 API / 日志 / 单测三路验证 → 收尾

「品质，长在结构里」的内在承诺：每一段被 AI 写出的代码，都先定了界、有人审了图、跑过了门控、留了回放。"可托付"不是流程写在文档里——是流程对每个 commit 都收一次口。

2. 架构全景——三层模型

「品质，长在结构里」—— 我们从结构开始建。一个项目对品构是 3 层：共享能力层 / 项目配置层 / 业务代码层。

2.1 三层架构

核心原则：L1 不含任何项目特定知识（无 webvirt、无 pangee）；L2 是项目的单一可信源；L3 只关心业务代码。

2.2 项目目录结构

.pg/
├── project.yaml                  # 统一配置 SSOT（六段结构）
├── changes/                      # pg-build caller 路由：变更提案与过程产物
│   ├── add-login-page/           # 某次变更
│   │   ├── proposal.md           # 做什么、为什么做
│   │   ├── design.md             # 怎么做、验证标准
│   │   ├── tasks.md              # stages × tracks  任务列表（含可选 review sub）
│   │   ├── execution-manifest.yaml  # 按 tasks.md 结构化生成的 pipeline 编排清单（runner 读取）；含 stages[i].environment 字段
│   │   └── 2-build/              # pipeline 过程产物（pipeline.events / 报告 / gate-score）
│   └── archive/                  # 已完成变更归档
├── regression/                   # pg-regression caller 路由：回归测试与问题清单
│   ├── frontend.json             # 生产代码问题清单（SSOT, 跨 run 累积）
│   ├── frontend--NN/       # 单次 run 目录（fix-issues / fix-test 留痕 + 报告）
│   └── ...
├── fix-issue/                    # pg-fix-issue caller 路由：bug 修复会话
│   └── fix--/  # 每次修复一个独立目录
│       └── dev-local/logs/       # hook 日志与产物
├── ad-hoc/                       # ad-hoc caller 路由：用户/agent 直接调 hook
│   └── auto--/        # 留空 --session 时自动生成
├── cronjobs/                     # 定时任务：crontab + opencode run 驱动批量任务
│   ├── run-opencode.sh           # 入口脚本（stash → master → opencode run → pop）
│   ├── prompt.txt                # 待执行提示词（git ignored）
│   └── cron.log                  # 定时执行日志
├── hooks/                        # 环境生命周期脚本（仅 environments 维度）
│   ├── role-backend-start.sh
│   ├── role-agent-start.sh
│   ├── env-dev-local-prepare.sh
│   └── ...
├── code-review/                  # review phase 的检查项源头（由 pg-init-project Phase 2.5 生成）
│   ├── code-review.yaml          # profile 索引（default + 语言 profile 的 Union）
│   ├── default/                  # 兜底 profile（含 design_alignment / scope_creep 等）
│   ├── java-spring/              # java/kotlin/scala 自动派发
│   ├── go/                       # go 自动派发
│   └── vue3/                     # ts/js/vue 自动派发
├── context/                      # 项目上下文快照（AGENTS.md 提取后缓存）
└── skills/                       # pg-skills 嵌入（git subtree），pg init 在 .opencode/ 创建 symlink

caller × session 双维度路由：上面 changes/ / regression/ / fix-issue/ / ad-hoc/ 四个目录由 PG_RUN_CALLER 决定一级目录，由 PG_RUN_SESSION 决定二级目录。runner 自动按调用方身份把日志、PID、result.json 写到对应路径，无需手动指定。cronjobs/ 不属于 hook 协议路由，由项目自管；典型场景是 crontab 触发 pg-regression 或 pg-propose 批量任务。

2.3 四层结构 —— 品质从哪里来

1.3 节讲了品构的方法论——SEA（方案 · 环境 · 验收）。那这些支柱是靠什么"钉死"的？靠四层结构，层层收紧：

层载体收紧什么解决什么问题
项目结构 project.yaml 模块 / 环境 / 实例 / 构建命令 不再猜"项目长什么样"
流程结构 stages × tracks × TDRVG 先做什么、再做什么、最后门控 不再猜"够不够"
产物结构 schema / template / 校验脚本 每个文件该长什么样、该含什么字段 不再猜"写没写全"
证据结构 事件溯源 pipeline.events 每步操作不可变、可回放 不再猜"谁干了什么"

每一层都是系统可以自动执行的契约，不是需要人记的规则。四层合在一起，才让"品质"这个抽象词变成可操作、可验证、可回放的具体机制。

品质，长在结构里——就是 SEA 三大支柱，被四层结构层层收紧的结果。

2.4 AGENTS.md 的角色

AGENTS.md 是 AI 的"入职手册"——包含项目的技术栈、包结构、数据库约定、编码风格、路径规范等。pg-propose 直接通读所有 AGENTS.md 提取上下文作为 LLM 约束，不生成中间缓存文件。

3. 新项目接入——Two Pillars

「品质，长在结构里」—— 我们先把骨架钉死在项目里。骨架对，AI 在里面写代码就是"合结构"的；骨架错，AI 写得越多越危险。

接入新项目，最重要的三件事：写对 project.yaml + 写对 hooks + 写对 .pg/code-review/

3.1 五步接入

  1. 配置 opencode 模型路由——pg-skills 使用三个路由别名 pg-router/pg-associate（轻量）、pg-router/pg-expert（主力）、 pg-router/pg-master（规划），需在 opencode.json 中映射到实际模型。 推荐使用 omniroute 或 9router 等工具进行模型路由选择。
  2. git subtree 拉入 pg-skills（含 .pg/skills/examples/code-review/ 模板：default / java-spring / go / vue3 / security 五个 profile）
  3. pg init 生成骨架 + symlink
  4. 重启 opencode（加载 slash commands + skills + sub-agents，含新 pg-build/review / pg-build/fix-review）
  5. 在 opencode 中触发 pg-init-project skill（AI 自动扫描仓库，生成 project.yaml + hooks + .pg/code-review/）
# ① 在 opencode.json 中配置模型路由
# 使用 omniroute / 9router 映射三模型：
#   pg-router/pg-associate → minimax-m2.7（轻量）
#   pg-router/pg-expert    → deepseek-v4-flash（主力）
#   pg-router/pg-master    → deepseek-v4-pro 或 minimax-m3（规划）

# ② 用 git subtree 把 pg-skills 同步进项目
git remote add pg-skills git@github.com:pin-gou/pg-skills.git
git fetch pg-skills
git subtree add --prefix=.pg/skills pg-skills v0.9.1 --squash

# ③ 跑 pg init 创建 .pg/ 骨架 + .opencode/ symlink
python3 .pg/skills/src/runtime/bin/pg init

# ④ 重启 opencode 后，在 opencode 中执行 pg-init-project
#    （Phase 1 扫仓库 → Phase 2 写 .pg/project.yaml → Phase 2.5 按 language 派发 review profile → Phase 3 写 .pg/hooks/ → Phase 4 doctor 校验）
# ⑤ 验证
python3 .pg/skills/src/runtime/bin/pg doctor
讲师强调：接入新项目最重要的三件事就是 ① 写对 project.yaml（骨架）、② 写对 hooks（血肉）、③ 写对 .pg/code-review/（review phase 的语言特异检查项源头）。这三件不对，AI 再怎么跑 pipeline 都是错的。

3.2 project.yaml —— 六段结构

modules 段

modules:
  backend:
    root: webvirt-backend
    language: java
    code_review_profiles: [security] # 可选 opt-in；java/go/proto 默认 security，ts/py 默认 standard，shell 默认 none
    build: .pg/hooks/backend-build.sh     # 虽在 hooks/ 下，但不走 hook 协议
    lint: cd webvirt-backend && mvn checkstyle:check  # 也可能 inline
    test:
      unit: .pg/hooks/backend-test.sh
      integration:
        cmd: .pg/hooks/backend-test.sh
        timeout_seconds: 3600

review 派发机制：review phase 由 pg-build 读取 .pg/code-review.yaml 全局 + module language 自动派发（Union 合并语义）。Security profile 由 pg-init-project Phase 2.5 推一份 .pg/code-review/security/ 后，在 .pg/code-review.yaml 中通过 union 合并拾起；按需在 modules.<m>.code_review_profiles 中追加 opt-in profile。是否派发 review 由 tracks.<id>.code_review_enabled 控制（默认 true；simple track 自动 false）。

environments 段

environments:
  dev-local:
    description: "本机全栈开发"
    describe_env: { script: .pg/hooks/env-dev-local-describe.sh, timeout_seconds: 120 }
    prepare_env:  { script: .pg/hooks/env-dev-local-prepare.sh, timeout_seconds: 300 }
    clean_env:    { script: .pg/hooks/env-dev-local-clean.sh, timeout_seconds: 120 }
    roles:
      - name: backend
        instances:
          - { name: backend-1, host: localhost, port: 9080 }
        actions:
          start: { script: .pg/hooks/role-backend-start.sh, timeout_seconds: 300 }
          stop:  { script: .pg/hooks/role-backend-stop.sh, timeout_seconds: 30 }
          logs:  { script: .pg/hooks/role-backend-logs.sh, args: ["{lines:100}"] }

tracks + stages 段

# tracks：定义在哪些 modules 上跑 TDRVG 循环（含 review 子阶段，由 pg-build 派发）
tracks:
  backend:
    modules: [backend, agent-proto]
    max_fix_retries: 5
    # review profile 由 .pg/code-review.yaml + module language 自动派发
  agent:
    modules: [agent, agent-proto]
  frontend:
    modules: [frontend]
  proto-gen:
    type: simple                       # simple track 自动跳过 review 阶段

# stages：定义 pipeline 阶段编排（on_conditions 决定 change 是否进入该 stage）
stages:
  - name: prepare-env-scripts
    tracks: [backend, agent, frontend]
    test_key: unit
    on_conditions:                       # 仅当改动命中 .pg/hooks/ 才启用
      - any_change_in: ["\\.pg/hooks/.*\\.sh$"]
  - name: dev
    tracks: [backend, agent, openapi-gen, frontend]
    test_key: unit
    gate: all_pass
    environment:
      required: true
tracks 字段速查：
  • modules：本 track 关联的 module id 列表（runner 用此定位 build/lint/test 命令）
  • max_fix_retries：verify→fix 子 pipeline 的总次数上限（默认 5）
  • type：standard（默认，TDRVG 四阶段 + 可选 review）/ simple（commands 列表直跑，自动跳过 review）/ scenario（真实集成场景测试，独立 scenario-prepare/execute/fix 三阶段，不参与 gate）
  • code_review_enabled：是否派发 pg-build/review agent。propose 阶段由 pg-gen-tasks-skeleton.py 按 manifest 的 phases.review 是否存在决定 tasks.md 含 4 还是 5 sub（不含 review 即 silent skip）；simple track 自动跳过 review
  • code_review_profiles：⚠ 已废弃，runner 不读取。profile 派发仅依赖 .pg/code-review.yaml 全局 + module language 自动派发。
  • type: scenario：独立三阶段（prepare/execute/fix），不参与 gate assessment。

3.3 Hook 协议详解

两条铁律

维度走 hook 协议？配置位置调度方式
Environments
prepare_env / clean_env / role start/stop/logs		 ✅ 走 hook .pg/hooks/<name>.sh ./pg-run（用户）/ pg-invoke-hook.py（agent）统一入口
Modules
build / lint / test		 ❌ 不走 hook project.yaml modules.<m>.{build,lint,test} Runner 直接 timeout N bash -c '<cmd>'
⚠ 常见误区：module 命令虽然可以是 .pg/hooks/backend-build.sh 这样指向脚本文件，但它是被 runner 当作普通 shell 命令执行的——没有 PG_* 注入，不走 hook 生命周期。是否走 hook 协议取决于配置在 project.yaml 的哪个位置，不在于是不是脚本文件。

Hook 标准模板

#!/usr/bin/env bash
# .pg/hooks/role-backend-start.sh
set -uo pipefail

# === 1. 加载 hook-helpers（必须）===
source "$PG_SKILLS_PATH/src/runtime/lib/hook-helpers.sh"
trap 'pg_fail_on_error $? $LINENO' ERR

# === 2. 业务逻辑 ===
start_backend() { ... }

# === 3. 报告结果 ===
DURATION=$(($(date +%s) - START))
pg_exit --status=pass --duration=$DURATION

# 失败时用 pg_fail：
# pg_fail --category=test_failure --code=PG-E-0601 \
#         --message="mvn test failed" --agent-recoverable=true

注入的环境变量（v5 协议）

变量说明适用范围

3.5 新项目接入 Checklist

接入流程的前 3 步（git subtree → pg init → pg-init-project）会自动生成 project.yaml、hooks 骨架、.pg/code-review/（Phase 2.5 按 language 派发）。但 AI 推断可能与实际项目有偏差，需要人工核对产物准确性，并通过 ./pg-run 对所有 hooks 做端到端测试验证。

  • git subtree 拉入 pg-skills → .pg/skills/（含 examples/code-review/ 模板目录）
  • pg init 生成骨架 + symlink
  • 在 opencode 中触发 pg-init-project skill（自动生成 project.yaml + hooks 模板 + .pg/code-review/）
  • 人工核对自动产物
  • modules：每个模块的根目录 + build/lint/test 命令是否准确
  • modules..code_review_profiles 是否按敏感度追加（java/go/proto 默认含 security；ts/py 默认 standard；shell 默认 none）
  • environments：环境列表、role 列表、actions 是否完整
  • tracks / stages：编排是否符合项目结构；tracks.<m>.code_review_enabled 是否需要为鉴权/协议模块开启
  • fix_issue / regression：参数是否合理
  • 每个 role 的 start / stop / logs 脚本：业务命令是否准确（CMD_PLACEHOLDER 是否替换）
  • 每个 env 的 prepare_env / clean_env 脚本：环境准备/清理逻辑是否对
  • lib/common.sh 是否复制到 .pg/hooks/lib/
  • .pg/code-review/ 是否按 language 派发（java → java-spring, go → go, ts → vue3）；security profile 未自动拷（opt-in）
  • （可选）声明 actions.health_check → pg-init-project 自动生成 health_check hook
  • 通过 pg-run 验证 hooks
  • pg doctor 校验（含 hooks/lib/common.sh 检查）
  • 人工 grep 验证 .pg/code-review/<language>/ 检查项细则文件存在（doctor 不覆盖）
  • ./pg-run --module <m> --action build/lint/test.<key> 验证 module 命令直跑
  • ./pg-run --env <env> --role <role> --instance <i> --action logs 验证 hook 可加载（只读）
  • 菜单 "准备环境并启动所有实例" → "停止所有实例并清理环境" 一键验证所有角色 + 环境级 hook（便捷）
  • 或单独验证：./pg-run --env <env> --role <role> --instance <i> --action start/stop + ./pg-run --env <env> --action prepare_env / clean_env
  • 配置 opencode 模型路由
  • opencode.json 中配置 model.router，将 pg-router/pg-associate / pg-expert / pg-master 映射到实际 LLM 模型（如 minimax-m2.7 / deepseek-v4-flash / deepseek-v4-pro 等）
  • 推荐使用 omniroute 或 9router 管理模型路由
关键提醒：project.yaml 的 modules.<m>.build 字段可以直接指向 .pg/hooks/ 下的脚本——比如 backend-build.sh 虽然是一个脚本文件，但它不在 hook 协议中，而是被 runner 当作普通 shell 命令执行。不要被"脚本在 hooks 目录下"误导，是否走 hook 协议取决于它在 project.yaml 的哪个位置。

4. 日常开发工作流

「品质，长在结构里」—— 我们让每一段都先出图再施工。这一章是品构的核心流：定界（Define）→ 提案（Propose）→ 构建（Build）→ 评审（Review）→ 合并（Merge）。

本章结构：4.1 全景路线图 → 4.2 定界 → 4.3 提案 → 4.4 构建。每节都讲核心机制 + 实操要点。

4.1 概述 —— 全景路线图

输入/输出对照表

阶段入口输入输出
1. 定界/1-pg-define模糊需求边界清单 + scope summary + define-summary.yaml
2. 提案/2-pg-propose边界 + project.yaml + .pg/code-review/proposal + design + tasks + execution-manifest.yaml
3. 构建/3-pg-build设计文档 + execution-manifest.yaml + project.yaml代码 + 测试 + 报告（含 review 阶段产物）+ 自动归档
4. 合并pg-verify-and-mergefeature branch合入 master

4.2 定界 —— `/1-pg-define`

定界：把用户脑海里的需求，和代码库里的真实代码"撞"在一起，通过多轮对话把方案与实施边界聊清楚的过程。

/1-pg-define 是一段自由对话，不是固定流程——没有脚本、没有强制产物。AI 是思考伙伴，陪你把三件事聊明白：

  1. 需求 × 现实代码 —— 不空谈，把想法落到代码库里：相关模块在哪、有没有同类实现、会动到谁
  2. 方案与边界 —— 做什么 / 不做什么、影响范围多大、怎么算做完（完成标准）
  3. 真实环境验收 —— 边界聊定后，讨论这个需求将来在真实环境里怎么验收（见下文「环境验证」）

这条探索有红线：只讨论、不写代码。AI 不做实现，正式产物由后续 /2-pg-propose 生成。

输入 → 产出

输入：用户的原始想法——可以很模糊（"实时协作"）、可以是具体问题、也可以是两个方案的比较，甚至没有参数直接开聊。

产出：口头对齐的 scope summary（边界 + 完成标准）。定界本身不落盘；唯一例外是结尾的「环境验证」，会落盘一份 define-summary.yaml（+ 只读探测产物 env-description.yaml），直接供 /2-pg-propose 使用。

定界后的环境验证

定界收尾时，AI 会带你把「将来怎么验收」讨论清楚——这是唯一会落盘、会调用 hook 的环节，目的是提前确认环境里有没有验收要的依赖（初始化数据、第三方服务等），免得 propose 时才发现缺东西。流程很轻：

  1. 定 change-id + 选环境 —— 给这次变更起个名（如 add-bucket-s3-info），并选一个目标 environment
  2. 只读探测真实环境 —— 通过 describe_env 探测（不启停服务、不写 DB），产出 env-description.yaml
  3. 逐个验收点讨论 —— 每个 V-* 需要环境提供什么能力（DB、对象存储、多租户…）、环境里有没有、缺了怎么降级，最终标记为 verifiable（可验证）/ degraded（降级）/ skipped（跳过）
  4. 落盘并校验 —— 写入 define-summary.yaml，过一遍机械校验

红线

  • 未经用户确认，不落盘、不调 hook
  • 验收讨论不滑向实现细节（那是 design.md 的事）
  • 不硬编码 IP / hostname / 端口，一律用 {env.…} 占位

定界之后，去哪？

环境验证通过后，AI 会用两个 question 跟你确认，不替你决定方向：

  • Q1 —— 验证方案够了吗？不够就回去继续细化；够了就进入下一步
  • Q2 —— 下一步走哪条路？
路径适用
/2-pg-propose（推荐）正经功能、跨模块、需要设计评审
/2b-pg-quick-build明确小改动、≤8 tasks、单 module
直接实施改文案/样式，无需任何 SKILL

4.3 提案 —— `/2-pg-propose`

提案：把定界聊出来的边界，变成一套"施工图纸"——proposal（做什么 / 为什么）、design（怎么做 / 怎么验证）、tasks（分步施工单）、manifest（执行清单）、scenario（端到端验收脚本）。图纸齐了，pg-build 就能无人值守施工。

这一段 AI 主要在写文档：不碰业务代码、不跑测试、不起服务。它把定界对话里的结论整理成一套结构化产物，落到 .pg/changes/<change-id>/ 下。

输入 → 产出

输入：定界产物（scope summary + define-summary.yaml）+ .pg/project.yaml（模块命令 / stages / environments 定义）

产出：5 份必填 + 按需扩展——

文件一句话解释
proposal.md做什么、为什么做（变更范围与理由）
design.md怎么做、怎么验证（接口设计 + V-* 验收标准）
tasks.md分步施工单：按 stage × track 切好的实施步骤，带进度 checkbox，支持断点续做
execution-manifest.yaml施工清单：stage 顺序、track 列表、选好的 environment——pg-build 的"总指挥"
1-propose-review/on-conditions-eval.md哪些 stage/track 启用、要不要 scenario 的决策记录（SSOT）
scenario-<track>.yaml（按需）端到端验收脚本（Gherkin），在真实环境里跑给需求做最终验收

三个关键决策

写图纸的过程中，AI 要定三件事：

  1. 哪些步骤要跑 —— 用 on_conditions 规则判断：只改了 OpenAPI 注解，就没必要重跑 hooks 相关步骤。命中就启用、没命中就跳过，避免每个变更都跑全流程
  2. 在哪个环境跑 —— 按 selection_rules 给每个 stage 选一个 environment（如 dev-local / dev-3tier）写进 manifest。环境选错要等 build 阶段才会暴露，所以这里得想清楚
  3. 要不要端到端验收 —— 跨模块联调 / 新 API / 多角色协作的变更，启用 scenario track 写 Gherkin 脚本；纯单模块改动（文档、SQL、单个 API）就不需要

一切都基于真实环境

图纸里的每个验收点（V-*）都锚定真实环境，不靠想象：

  • env-description.yaml —— 定界阶段 describe_env 探测出的环境资源清单（有哪些 DB、缓存、第三方服务、数据状态）。所有产物写验收时都要引用它，不允许拿"环境未就绪"当借口跳过
  • define-summary.yaml —— 定界阶段和用户聊好的每个 V-* 的验收方式（verifiable 可验证 / degraded 降级 / skipped 跳过），这里直接沿用，不再重新讨论

一次机械校验把关

所有产物写完，跑 pg-validate-proposal.py 做唯一校验：文件是否齐全、占位符有没有漏填、tasks / manifest / scenario 三份产物是否对得上。不过就不放行，修复到通过为止。校验通过后，就可以喊 /3-pg-build 开工了。

4.4 构建 —— `/3-pg-build`（基于事件溯源引擎）

"图纸审完了，Runner 开始施工。人只做一件事：执行命令等结果。"

一句话理解

/3-pg-build 是施工阶段。它读取 propose 画好的图纸，按 execution-manifest.yaml 的编排，把「写代码 → 跑测试 → 审查 → 验证 → 打分」全部自动跑完。AI 在过程中反复做一件简单的事：

  1. 问 Runner 下一步做什么（next）——Runner 说派哪个 sub-agent，就派哪个
  2. 派 sub-agent 干活——写测试、写代码、审查、验证……每个阶段一个专门的 agent
  3. 记录结果（record）——写进 pipeline.events（append-only 事件流）
  4. 回到第 1 步——直到 Runner 说 done（触发合并）或 workflow_failed（需要人工介入）

这套循环由事件溯源驱动：每一步都是一个不可变事件，状态随时从事件流重新推导。好处是——跑挂了能精确恢复到断点，不从头再来。

三种干活方式（track）

不同性质的活，用不同的 track 类型（propose 阶段已在图纸里标好）：

类型怎么干适合
standard（默认）sub-agent 按 TDRVG 五阶段走，质量门把关正经功能开发、跨模块改动
simple按命令列表直接跑，命令 exit 0 即通过代码生成、文档同步、模板替换等纯机械活
scenario启动真实环境，跑 Gherkin 场景，跑通过为止跨模块联调、端到端验收

质量把关：TDRVG 五阶段

standard track 默认走 5 步，每步一个专门的 sub-agent：

  1. T · Test（红） —— 先写测试，让失败先发生
  2. D · Dev（绿） —— 实现代码，让测试变绿
  3. R · Review —— 静态审查：实现和设计对得上吗？有没有范围蔓延？模式一不一致？发现问题 → fix-review 修复后重审
  4. V · Verify —— 运行时验证：启动服务，逐项跑 design.md 里的 V-* 验收点。不过 → fix 修复后重跑
  5. G · Gate —— 5 维加权打分，总分 ≥80 才放行

其中 review / verify / gate 三个质量门可按需关闭（纯文档改动就没必要上全套），但 verify 和 gate 至少留一个，免得没有质量把关。修复循环都有次数上限（max_fix_retries），修不动就终止，把问题交给用户，不硬扛。

打分门（gate-score）

gate 不看"过 / 不过"这种二值，而是按 5 个维度打分，总分 ≥80 通过：

维度权重看什么
correctness35%行为符合提案吗？测试覆盖关键路径吗？
security25%权限校验、敏感信息、依赖漏洞
maintainability15%命名规范、模块边界、日志规范
performance15%关键路径延迟、N+1 查询、资源占用
spec_coverage10%design 的验收点都被覆盖了吗？

不够 80 分，就把弱项交给 fix-gate 定向补；补不动就走人工评审。各 track 的评分汇总成 gate-assessment.md——final-gate 没有它就不放行，保证"没评审就不合入"。

真实环境，真实验收

需要环境的 stage，Runner 进出都会自动 prepare_env / clean_env，不用人插手。scenario 验收更是在真实服务实例上跑：先重启实例，再执行 Gherkin 场景（Given / When / Then），失败就派 scenario-fix 诊断修复后重跑，跑通过为止。每个验收点（V-*）早在定界阶段就和用户确认过可验证 / 降级 / 跳过，这里照做即可。

失败与恢复

跑挂了不慌：Runner 用事件流 + tasks.md 的 checkbox 记住进度，重跑时从第一个没打勾的章节接着干，而不是从头再来。只有修到"修不动"（循环次数耗尽、环境漂移 / 设计漂移）才终止，把决定权交回给用户。

收尾

所有 track 完成后，final-gate 做跨 track 的最终门控。通过后 Runner 自动收尾：每步提交代码、归档到 changes/archive/，然后触发 pg-verify-and-merge 完成合并。至此一次变更走完「定界 → 提案 → 构建 → 合并」全流程。

5. Bug 修复工作流

「品质，长在结构里」—— LLM 自主完成：诊断 → 修复 → 真实环境验证。本 SKILL 只提供 LLM 无法自行发现的 pg-* 基础设施协议。

5.1 一句话理解

/5-pg-fix-issue 是修 Bug 的流程。核心不是"改完交差"，而是用真实环境证明修好了。与传统方式最大的区别：

传统修复

人工看日志 → 猜根因 → 改代码 → 提交 → CI 跑测试 → 修得对不对完全看人品

pg-skills 修复

配置加载 + 环境探测 → 系统化诊断 → 展示方案 → 用户确认 → 修复 → 真实环境验证 → 收尾留证据

5.2 五步流程

  1. 启动准备 —— 加载配置（模块命令、环境定义），并用 describe_env 只读探测目标环境（不启停服务），拿到环境全貌：有哪些服务、DB 通不通、数据在不在
  2. 诊断 —— 对照环境信息和代码探索，定位根因
  3. 展示方案 —— 根因分析 + 修复计划 + 验证方式，等用户确认后才动手
  4. 修复 —— 改代码
  5. 验证（硬性） —— 启动受影响服务 → 真实 API 调用 → 查服务日志 → 跑单测，修到通过为止

验证是硬性要求，不是可选项

  • 环境起不来 → 必须明说"未做端到端验证"，不糊弄
  • 验证命令的输出原样给用户看，不润色
  • 验证不过 → 继续修，直到通过，或如实报告无法修复

5.3 收尾要求

  • 不留 DIAG / 临时日志 / 临时脚本
  • git diff 只含目标文件的变更
  • 向用户交代三件事：根因 + 改了什么 + 验证证据

5.4 两条红线

  • 占位符 —— host / port / role / instance 一律从 project.yaml 读，禁止硬编码 localhost:9080 这类示例值
  • hook 调用 —— 必须走 pg-invoke-hook.py 协议（带审计 / 日志 / 超时），禁止直接 bash .pg/hooks/*.sh
触发方式：在 opencode 中输入 /5-pg-fix-issue，然后描述问题。例如：
用户创建 VM 时，状态一直 CREATING 不变成 RUNNING

Q&A

Build 跑到一半失败了怎么办？

查看 .pg/changes/<name>/2-build/*.md 中的报告。gate 或 verify 报告会写明失败原因。修复后重跑 /3-pg-build。

怎么知道当前 pipeline 跑到哪一步了？

查看 .pg/changes/<name>/2-build/pipeline.events（append-only JSONL），或调 pg-pipeline-runner.py progress <change> 看人类可读摘要。

提案产出后想改一两处，怎么改？

直接编辑对应的 markdown / yaml 产物（proposal.md / design.md / tasks.md / scenario-<track>.yaml / execution-manifest.yaml）即可；如果改了 design.md 的接口、数据结构或 stage/tracks 编排，必须重跑 /2-pg-propose 让 execution-manifest.yaml 重新生成。

怎么新增一个回归测试套件？

编辑 .pg/project.yaml 的 regression.suite 段，增加一个新 suite 配置：

regression:
  suite:
    my-new-suite:
      environment:
        name: dev-local
        required_roles: []
      module: backend
      test_keys: [unit]
怎么加一个测试环境（比如 staging）？

编辑 .pg/project.yaml 的 environments 段，新增一个环境 + 各 role 的 actions。然后为该环境编写对应的 hook 脚本（prepare_env / clean_env / role start/stop/logs）。

pg-skills 版本怎么升级？
# 升级到最新版
pg upgrade

# 升级到指定版
pg upgrade v0.9.1

# 查看远程可用版本
pg upgrade --list

# 校验
pg doctor
怎么验证 hooks 写得对不对？

用 ./pg-run 的 logs 动作（只读操作，安全无害）验证 hook 脚本是否能正常加载并执行：

./pg-run --env dev-local --role backend --instance backend-1 --action logs --tail-lines 10
module 命令和 hook 脚本的区别到底是什么？

核心区别两点：

  1. 是否有 PG_* 注入：hook 脚本有 $PG_ROLE、$PG_ENV 等；module 命令没有
  2. 错误处理方式：hook 脚本用 pg_exit / pg_fail 写 result.json；module 命令只看 exit code

判断标准很简单：看它在 project.yaml 中配置在哪个位置——modules 下的都是 module 命令，environments 下的都是 hook。

propose 之后只改了一行产品描述，要不要再 propose 一遍？

文案 / 术语 / 数字这类纯文档微调，直接编辑对应的 markdown 产物即可；如果改了 design.md 的接口、数据结构或 stage/tracks 编排，必须重跑 /2-pg-propose 让 execution-manifest.yaml 重新生成。

feat/pg/<change> 分支要 push 吗？要不要 PR？

pg-build 完成后会自动调 pg-verify-and-merge 模拟合 master → 真合 master；本机操作不必手动 push。多机协作时仍需 git push origin feat/pg/<change> 让 CI 跑；pg-verify-and-merge 处理实际的合并逻辑。

从 0.7.x 升 0.8.x 后，旧 change 还能 build 吗？

可以。0.8.x 向后兼容 0.7.x 的 execution-manifest.yaml 形态；但含 review 子阶段的 tasks.md需要用 pg-gen-tasks-skeleton.py --selected-stages 重新生成一次，章节号 N 会重排（下游消费方必须读 sections JSON 的 N 值，不要硬编码）。0.8.2 新增 manifest v3（enabled 必填字段），旧 manifest 升级后需补充该字段。具体迁移步骤见 pg upgrade 升级日志。

多人同时跑 pg-init-project 谁最后说了算？

pg init 幂等可重跑；但 pg-init-project 是 AI 推断，生成完一定要人工 review（参见 §3.5 checklist "人工核对自动产物" 段）。建议先在分支跑一次 → PR 合 master → 其他人 rebase。.pg/code-review/ 目录 Phase 2.5 幂等，不会自动覆盖已存在文件。
